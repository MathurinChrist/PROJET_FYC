IW 33 & 34 · cours original

Création d’un shell Linux avec Node.js

À la découverte de la ligne de commande et du système d’exploitation Linux. Deux séances, un seul fil : écrire nysh, un shell qui marche vraiment.

Un shell n’est pas un « terminal coloré ». C’est le programme qui lit ce que tu tapes, le comprend, lance d’autres programmes, et recable stdin, stdout et stderr. En le reconstruisant, on touche au métal de Linux sans quitter JavaScript.

Objectifs

  • Comprendre le modèle Unix : processus, fichiers, descripteurs, PATH.
  • Écrire un REPL Node.js qui se comporte comme un petit bash.
  • Distinguer commande interne et commande externe — et pourquoi cd ne peut pas être un processus fils.
  • Implémenter pipes, redirections, variables, opérateurs && / ||.

Organisation

34 — Un vrai shell~4 hPipes, redirs, env, signaux

Séance 33 · leçon 1

Qu’est-ce qu’un shell ?

Quand tu ouvres « le terminal », tu vois trois couches empilées :

  1. Le terminal (fenêtre, tty) : affiche des caractères, capte le clavier.
  2. Le shell (bash, zsh, nysh) : interprète les lignes, lance des programmes.
  3. Les programmes (ls, git, node) : font le travail.

ls n’est pas une fonction du shell. C’est un binaire, souvent /usr/bin/ls. Le shell le trouve grâce à PATH, le démarre, et lui donne tes arguments.

$ type ls
ls is /usr/bin/ls

$ type cd
cd is a shell builtin

Cette distinction est le cœur du cours. ls peut vivre dans un autre processus. cd doit changer le répertoire du shell lui-même.

Piège Si tu lances cd avec child_process.spawn, le fils change de dossier puis meurt. Le père n’a pas bougé. Le prompt reste au même endroit. C’est le premier test de maturité d’un shell.

Séance 33 · leçon 2

Linux vu du terminal

Linux expose le monde comme des fichiers. Un dossier, un disque, un pipe, même le clavier : un descripteur, un chemin, des permissions.

ConceptCe que tu en vois
Répertoire courantpwd, variable PWD
Home~, $HOME
PATHliste de dossiers où chercher les binaires
Permissionslire / écrire / exécuter (rwx)
Environnementpaires NOM=valeur héritées par les fils

Une commande tapée est une phrase :

ls -la ./src

Le premier mot est le programme. Les suivants sont des arguments. Le shell ne « sait » pas ce qu’est -la : il le transmet tel quel à ls.

Le prompt

Convention POSIX : user@host:chemin$ (le # est réservé à root). nysh reprend ce contrat, en vert et bleu, pour que le répertoire courant soit toujours visible — c’est ton ancrage mental.

Séance 33 · leçon 3

Processus, PID, fork et exec

Un processus est un programme en train de s’exécuter : son PID, sa mémoire, ses descripteurs 0/1/2, son répertoire courant, son environnement.

Le modèle Unix classique :

1. fork() → clone le shell 2. exec() → le clone devient `ls` 3. wait() → le shell attend la fin 4. prompt → on recommence

Node.js n’expose pas fork+exec à la main dans nysh. On utilise child_process.spawn, qui fait ce travail : créer un fils, lui passer argv, cwd, env, et les flux.

import { spawn } from "node:child_process";

const child = spawn("ls", ["-la"], {
  cwd: ctx.cwd,
  env: ctx.env,
  stdio: "inherit",
});
child.on("close", (code) => { /* code de retour */ });

Le code de retour vaut 0 si tout va bien, autre chose sinon. C’est ce que testeront && et || à la séance 34. Convention : commande introuvable → 127.

Séance 33 · leçon 4

Node.js parle au système

Quatre modules suffisent pour un shell :

ModuleRôle dans nysh
readlinelire une ligne, historique, complétion, Ctrl+C / Ctrl+D
child_processlancer les binaires du PATH
fs / pathcd, redirections, globbing
processenv, cwd, stdin/stdout, PID, exit

Architecture du projet — chaque fichier est une étape mentale :

ligne tapée → tokenizer.js (mots et opérateurs) → parser.js (arbre : pipelines, &&, redirs) → expander.js ($VAR, ~, *) → executor.js (spawn + builtins) → prompt suivant

Tu n’as pas besoin d’une librairie. Node 18+ suffit. Moins de magie, plus de Linux.

Séance 33 · TP 1

La boucle REPL

REPL : Read, Eval, Print, Loop. Un shell est un REPL dont « Eval » signifie « exécuter une ligne Unix ».

Fichier src/shell.js : readline.createInterface, un prompt, un handler line.

const rl = readline.createInterface({
  input: process.stdin,
  output: process.stdout,
  prompt: buildPrompt(ctx),
});
rl.on("line", async (line) => {
  await runLine(line, ctx);
  rl.setPrompt(buildPrompt(ctx));
  rl.prompt();
});
À faire Lance node src/index.js. Vérifie que Ctrl+D quitte, que exit quitte, qu’une ligne vide ne explose pas. Le prompt doit afficher ~ quand tu es dans $HOME.

Le contexte ctx est l’état du shell : cwd, env, lastStatus, aliases. C’est l’équivalent de la mémoire de bash. Tout ce qui survit d’une ligne à l’autre vit là.

Séance 33 · TP 2

Découper la ligne : le tokenizer

Avant de comprendre, il faut découper. echo "hello world" | cat n’est pas 5 mots : hello world est un seul argument, | n’est pas un argument, c’est un opérateur.

Règles que nysh reprend de POSIX :

  • Les espaces séparent les mots, sauf entre quotes.
  • '...' : littéral. $USER n’est pas expansé.
  • "..." : les variables sont expansées, les espaces restent dans le mot.
  • # commence un commentaire jusqu’à la fin de ligne.
  • |, ||, &&, ;, >, >>, < sont des tokens à part.
tokenize(`echo "hi there" | cat > out`)
// WORD echo | WORD hi there | PIPE | WORD cat | REDIR_OUT | WORD out
Piège | et || se ressemblent. Il faut regarder deux caractères en avant (lookahead). Même chose pour > et >>, & et &&.

Séance 33 · TP 3

Commandes internes

Une commande interne s’exécute dans le processus nysh. Liste minimale d’un shell vivant :

CommandePourquoi elle est interne
cdchange ctx.cwd
export / unsetmutent ctx.env
exittermine le REPL
aliasmémoire du shell
echo, pwdpratiques, et echo doit connaître $? après expansion

cd - revient à OLDPWD. C’est un détail, mais c’est exactement le genre de détail qui prouve qu’on a compris l’état du shell.

À faire cd playground && pwd && cd - && pwd. Les deux pwd doivent afficher des chemins différents. Si ce n’est pas le cas, tu as spawn cd.

Séance 33 · TP 4

Commandes externes et PATH

Si le premier mot n’est pas un builtin, nysh cherche un exécutable :

  1. S’il contient un /, c’est un chemin (./script.sh, /usr/bin/ls).
  2. Sinon, on parcourt $PATH dans l’ordre, et on prend le premier fichier exécutable.
  3. Sinon : message commande introuvable, status 127.

type ls et which ls rendent ce mécanisme visible. type dit aussi si c’est un alias ou un builtin — c’est un outil d’introspection, pas un gadget.

nysh$ type cd
cd est une commande interne du shell
nysh$ type ls
ls est /usr/bin/ls

Le fils hérite de cwd et de env. C’est pour ça qu’après export FOO=1, un python3 -c 'import os; print(os.environ["FOO"])' affiche 1.

Séance 34 · leçon 1

Carte du code

On reprend le même dépôt. La séance 34 n’ajoute pas un nouveau projet : elle branche les tuyaux.

FichierCe qu’on y étend
parser.jsredirections, pipes, && || ; &
expander.js$VAR, $?, ~, globs * ?
executor.jsfd, pipes, spawn
history.js / completer.jsconfort d’un vrai tty

Grille mentale de la grammaire :

ligne = and_or ( ';' and_or )* and_or = pipeline ( '&&' | '||' pipeline )* pipeline = command ( '|' command )* command = mots redirections

On parse d’abord la structure (opérateurs), on expanse ensuite les mots. Inverser cet ordre casserait echo $x | cat si $x contenait un |.

Séance 34 · leçon 2

Descripteurs 0, 1 et 2

Chaque processus naît avec trois descripteurs :

fdNomPar défaut
0stdinclavier
1stdoutécran
2stderrécran (séparé, pour ne pas polluer les pipes)

Rediriger, c’est substituer un fichier (ou un pipe) à l’un de ces trois fd avant d’exécuter la commande. Le programme, lui, continue d’écrire sur 1 : il ne sait pas si 1 est un terminal ou out.txt.

C’est pour ça que ls > fichiers.txt ne demande aucune option spéciale à ls. Le shell a changé le décor, pas le rôle.

Expérience Dans nysh : echo visible > playground/out.txt puis cat playground/out.txt. Ensuite ls /dossier-absent 2> playground/err.txt — le message d’erreur n’apparaît plus à l’écran.

Séance 34 · leçon 3

Redirections

nysh implémente le kit POSIX usuel :

SyntaxeEffet
cmd > fstdout écrase f
cmd >> fstdout ajoute à f
cmd < fstdin lit f
cmd 2> fstderr écrase f
cmd 2>> fstderr ajoute à f

Dans l’exécuteur, on openSync le fichier avec le bon flag (w, a, r) et on passe le numéro de descripteur à spawn. Pas besoin de recopier les octets nous-mêmes : le noyau écrit directement dans le fichier.

const fd = fs.openSync(file, "w");
spawn("ls", [], { stdio: ["inherit", fd, "inherit"] });
Piège Fermer le fd trop tôt (avant la fin du fils) coupe l’écriture. Attendre l’événement close du processus, puis fermer notre copie du descripteur.

Séance 34 · leçon 4

Pipes

Un pipe est un tampon noyau avec deux bouts : on écrit à gauche, on lit à droite. La ligne

echo hello-pipe | cat

veut dire : stdout de echo = bout écriture, stdin de cat = bout lecture. Plus d’écran au milieu.

En Node, un PassThrough joue ce rôle pédagogique. On lance les commandes du pipeline en parallèle (Promise.all) : si on attendait la fin de la première avant de démarrer la seconde, un pipe plein bloquerait l’écrivain pour toujours (deadlock classique).

Les builtins dans un pipe doivent écrire dans le tuyau, pas sur le terminal — et appeler .end() pour envoyer EOF, sinon cat attend indéfiniment.

À faire echo hello-pipe | cat > playground/pipe.txt puis cat playground/pipe.txt. Enchaîne ls | grep src | wc -l (binaires du système, pas des builtins).

Séance 34 · leçon 5

Environnement et expansions

Avant d’exécuter, chaque mot passe dans expander.js, dans cet ordre :

  1. Variables : $NAME, ${NAME}, $? (dernier status), $$ (PID).
  2. Tilde : ~ → $HOME.
  3. Globbing : * et ?, seulement hors quotes.
export PROJET=nysh
echo "cours $PROJET"     # cours nysh
echo '$PROJET'           # $PROJET
echo *.js                # fichiers .js du cwd
echo $?

export écrit dans ctx.env, objet que l’on passe à spawn. Un fils Python ou un bash -c voit donc les mêmes variables. unset les retire.

Les quotes simples gèlent tout. Les doubles gardent les espaces et expansent les dollars. C’est le contrat que les utilisateurs de bash ont dans les doigts : le respecter, c’est déjà faire un vrai shell.

Séance 34 · leçon 6

Opérateurs de contrôle

OpérateurSémantique
;enchaîner, toujours
&&n’exécuter la suite que si status == 0
||n’exécuter la suite que si status != 0
&lancer en arrière-plan, rendre le prompt tout de suite
 
true && echo OUI
false && echo NON      # silence
false || echo FALLBACK
pwd ; echo ensuite

Ces opérateurs travaillent sur le status, pas sur le texte affiché. false peut ne rien imprimer et quand même valoir 1. D’où les builtins true et false : ce sont des outils pédagogiques, pas des gadgets.

Séance 34 · leçon 7

Signaux, historique, complétion

Signaux

Ctrl+C envoie SIGINT. Un shell interactif ne doit pas mourir : il abandonne la ligne, affiche un nouveau prompt. Ctrl+D (EOF sur une ligne vide) quitte — comme bash.

readline émet SIGINT sur l’interface. nysh réaffiche le prompt au lieu d’appeler process.exit.

Historique

Les flèches haut/bas viennent de readline. On persiste en plus dans ~/.nysh_history pour retrouver les commandes d’une session à l’autre. history les liste.

Complétion

Tab complète : d’abord les builtins et le PATH si on est sur le premier mot, sinon les fichiers du cwd. Les dossiers reçoivent un / final, comme dans bash.

Les alias (ll=ls -al est prédéfini) se développent avant l’exécution. type ll le montre.

Séance 34 · TP final

Assembler le shell complet

Scénario à jouer dans nysh, sans tricher avec bash :

cd playground
echo "nysh est un shell" > notes.txt
cat notes.txt | grep nysh
export PROJET=IW-33-34
echo "cours $PROJET" >> notes.txt
cat notes.txt
true && echo OK
false || echo KO
ls *.txt
type cd
type ls
help
exit

Fichier script : node src/index.js playground/demo.nysh.

Extensions possibles 2>&1, heredocs <<, jobs fg/bg, glob **, substitution de commande $(...). Chacune est un bon sujet de bonus, pas un prérequis du rendu.

Séance 34 · ouverture

Au-delà de nysh

bash, dash, zsh, fish : tous parlent à peu près POSIX, puis ajoutent des dialectes. Ce que nysh a volontairement laissé de côté :

  • fonctions shell, if/for/while ;
  • job control complet (Ctrl+Z, jobs) ;
  • expansion arithmétique $((1+1)) ;
  • coprocessus, process substitution <(cmd).

Ce n’est pas un échec : c’est le périmètre d’un atelier. En deux séances, tu as reconstruit la boucle qui fait tourner Linux au quotidien — lire une ligne, la comprendre, recabler 0/1/2, attendre un status.

Le meilleur test n’est pas « est-ce identique à bash ? ». C’est : est-ce que je peux expliquer chaque caractère d’une ligne comme ls | grep js > out && echo ok ? Si oui, le cours a tenu sa promesse.

nysh$ echo "fin du cours $?" 
# et maintenant, relis src/executor.js à voix haute.
